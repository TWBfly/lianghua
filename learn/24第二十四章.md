# 三、什么时候 Agent 才有意义？

### Evidence Acquisition（证据获取）

### Multi-Step Judgment（多步骤判断）

7. 查行业环境；
8. 用 Python 算利息覆盖率；
9. 评估相互矛盾证据；
10. 输出概率。

这就很适合 Agent。

# 七、第24章第二部分：Cognitive Architectures

# 八、ReAct 是什么？

### ReAct

### Reason + Act

### 推理 + 行动

基本循环：

```text
Thought
↓
Action
↓
Observation
↓
Thought
↓
Action
```

通俗讲：

> 先想下一步需要什么证据，然后调用工具，再看结果，再决定下一步。

---

# 九、举个金融例子

问题：

> “A公司未来一年违约风险是否显著上升？”

Agent：

```text
Thought:
先检查债务结构

Action:
读取10-K债务章节

Observation:
2027年有大额债务到期
```

再：

```text
Thought:
需要确认现金覆盖能力

Action:
读取资产负债表和现金流
```

再：

```text
Observation:
现金下降，FCF为负
```

最后：

> 才综合判断。

这就是 ReAct。

# 十、为什么作者把 ReAct 当默认？

因为它：

### Grounded（容易基于工具结果）

### Auditable（可审计）

### Cheap（相对便宜）

### Simple（简单）

所以大部分金融研究工作流：

> ReAct 已经够用。

---

# 十一、Tree of Thoughts 是什么？

### Tree of Thoughts（思维树）

不是只走：

$$
A\rightarrow B\rightarrow C
$$

一条路径。

而是：

```text
Hypothesis A
├── path 1
├── path 2
Hypothesis B
├── path 1
├── path 2
```

然后比较：

> 哪条推理路线最好。

---

# 十二、什么时候才值得 Tree of Thoughts？

例如一个问题：

> “某资产暴跌到底是基本面、流动性还是技术性踩踏？”

你可以同时展开：

### Hypothesis 1

基本面恶化。

### Hypothesis 2

Forced Liquidation（被迫平仓）。

### Hypothesis 3

Cross-Market Spillover（跨市场传染）。

然后分别寻找证据。

这种：

> branch-heavy（分支很多）的任务。

才值得用。

---

# 十三、为什么不能所有问题都 Tree of Thoughts？

因为成本：

$$
TokenCost\uparrow
$$

$$
Latency\uparrow
$$

而且分支越多：

> 不一定质量越高。

所以作者强调：

### Reasoning Budget（推理预算）

必须控制。

---

# 十四、Reflexion 是什么？

### Reflexion（反思式智能体）

Agent 做完一次任务后：

> 评价自己的错误。

并把经验写进 memory（记忆）。

下一次：

> 使用这些经验改进。

比如：

第一次：

> 因为漏掉债务脚注，预测错了。

记忆：

> “研究信用风险时必须检查 debt maturity footnote。”

下次：

> 会主动查。

---

# 十五、听起来很强，但危险在哪里？

如果 memory 里写进去的是：

> 错误总结。

那 Agent 会：

> 永久重复错误。

所以作者强调：

### Memory Governance（记忆治理）

Reflexion 只有在：

> 明确 memory 质量控制存在时才值得使用。

---

# 十六、第24章第三部分：Agent Memory

这个部分我认为对你的 Agent 项目尤其重要。

很多人所谓 memory：

> 就是把历史聊天全部塞进去。

作者认为这不够。

Agent memory 应该分：

### Working Memory（工作记忆）

当前任务正在用的东西。

### Short-Term Memory（短期记忆）

最近几步结果。

### Long-Term Memory（长期记忆）

跨任务保存的知识。

---

# 十七、为什么不能只靠聊天历史？

因为聊天历史：

* schema 不固定；
* 不好搜索；
* 不好版本化；
* 不好评估；
* 不好回放；
* 不好审计。

所以 Agent 真正需要的是：

### Typed State（类型化状态）

---

# 十八、什么叫 Typed State？

例如：

```python
ResearchState:
    question
    probability
    evidence
    source_ids
    contradictions
    missing_items
    step_count
    status
```

而不是：

> 一坨自由文本。

这样每一部分：

> 都可检查。

---

# 十九、为什么 State 这么重要？

因为你需要回答：

> Agent为什么给出这个结论？

如果只有最终答案：

> 无法复盘。

如果 state 中记录：

* 搜过什么；
* 看了什么；
* 哪条证据改变了概率；
* 哪一步失败；

就能：

### Replay（回放）

---

# 二十、Checkpoint 是什么？

### Checkpoint（检查点）

每执行若干步：

> 保存整个 Agent State。

例如：

```text
Step 0
Step 3
Step 7
Final
```

这样如果 Step 8 崩了：

> 可以从 Step 7 恢复。

也可以做：

> A/B comparison（A/B比较）。

---

# 二十一、Replay 为什么对量化特别重要？

假设 Agent 2026-09-01 给出：

$$
P(Recession)=35\%
$$

三个月后事件结果出来。

你需要：

> 精确重放当时它看到了哪些信息。

否则：

> 你根本无法评估预测质量。

这就是：

### Post-Outcome Evaluation（事后结果评估）

---

# 二十二、State Versioning 又是什么？

### Schema Versioning（状态模式版本）

Agent V1：

```text
evidence
probability
```

Agent V2：

新增：

```text
source_quality
contradictions
```

那么历史 checkpoint：

> 怎么兼容？

所以必须：

$$
state\_version
$$

这和数据库 schema evolution（模式演进）一样。

# 二十四、什么叫 Tool Contract？

假设 Agent 有一个：

### Search Tool（搜索工具）

不能只定义：

> “search(query)”。

最好返回固定结构：

```text
title
source
date
content
confidence
citation
```

这就是：

### Structured Output（结构化输出）

---

# 二十五、为什么 Tool Contract 很重要？

如果工具返回：

> 完全自由文本。

Agent 很难判断：

* 哪个字段是时间；
* 哪个是来源；
* 哪个是数值；
* 哪个是正文。

结构化以后：

> 才能稳定处理。

---

# 二十六、Provenance Enrichment 是什么？

### Provenance Enrichment（来源增强）

工具返回的不只是：

> “结果内容”。

还应该带：

* Source URL / ID；
* timestamp；
* provider；
* document type；
* retrieval time。

这样最终答案：

> 才有审计链。

---

# 二十七、Source Policy 是什么？

### Source Policy（来源策略）

金融 Agent 不应该：

> 随便所有网页权重一样。

可以定义：

```text
Tier 1:
SEC filings
官方统计
公司公告

Tier 2:
Reuters
Bloomberg
WSJ

Tier 3:
Secondary blogs
论坛
```

Agent 在冲突时：

> 优先高等级来源。

---

# 二十八、Context Engineering 是什么？

### Context Engineering（上下文工程）

不是简单 Prompt Engineering（提示词工程）。

它更广：

> 决定模型每一步到底看到哪些信息。

包括：

* 当前 state；
* 哪些 tool outputs；
* 哪些 memory；
* 哪些 source；
* 哪些 instructions。

上下文太多：

> 噪声。

太少：

> 信息不足。

# 三十五、第24章第六部分：Research Agent

这是第24章第一大 Capstone（综合项目）。

作者构建：

### ResearchAgent（研究智能体）

# 三十六、为什么输出 Probability（概率）而不是“会/不会”？

因为金融和宏观问题：

> 高度不确定。

说：

> “一定会发生。”

通常不专业。

更合理：

$$
P=65\%
$$

然后未来事件解决后：

> 可以评分。

---

# 三十七、这就进入 Proper Scoring Rules

### Proper Scoring Rules（严格适当评分规则）

意思：

> 专门评价概率预测是否准确。

第24章后面用：

### Brier Score

### Log Score

### ECE

---

# 三十八、Brier Score 是什么？

### Brier Score（布里尔分数）

对于二元事件：

$$
BS=(p-y)^2
$$

其中：

$$
p
$$

预测概率。

$$
y\in\{0,1\}
$$

实际结果。

---

# 三十九、举例

预测：

$$
p=0.8
$$

事件发生：

$$
y=1
$$

那么：

$$
BS=(0.8-1)^2=0.04
$$

不错。

如果事件没发生：

$$
BS=(0.8-0)^2=0.64
$$

很差。

---

# 四十、为什么这比 Accuracy（准确率）更好？

如果两个 Agent 都预测：

> 会发生。

一个：

$$
51\%
$$

一个：

$$
99\%
$$

结果失败。

准确率：

> 两个都错。

Brier：

> 99%的那个罚得更重。

因为它：

> 过度自信。

---

# 四十一、Calibration 是什么？

### Calibration（概率校准）

如果 Agent 所有：

$$
70\%
$$

预测里。

最终真的约：

$$
70\%
$$

发生。

说明：

> calibration 好。

---

# 四十二、为什么金融研究特别应该输出校准概率？

因为这可以直接支持：

### Decision Threshold（决策阈值）

例如：

$$
P>70\%
$$

才采取某种研究行动。

也能：

> 比较不同 Agent 的质量。

---

# 四十三、第24章第七部分：Multi-Agent Forecasting

这部分很有意思。

作者不是默认：

> 多 Agent 一定比单 Agent 好。

而是研究：

> 多 Agent 什么时候真的提供增量。

---

# 四十四、多 Agent 为什么可能有价值？

因为不同 Agent：

> 可能产生不同证据路径。

例如：

### Agent A

偏基本面。

### Agent B

偏宏观。

### Agent C

偏市场数据。

然后输出：

$$
p_A,p_B,p_C
$$

最后 aggregation（聚合）。

---

# 四十五、但作者有一个反常识实验

不一定非要给不同 Agent 不同角色。

作者 `06_multi_agent_research` 研究：

> 多个相同 Agent，只通过 temperature diversity（温度差异）就能产生不同答案。

也就是说：

> diversity（多样性）不一定必须来自角色设定。

---

# 四十六、为什么 Multi-Agent 的关键是 Correlation？

假设5个 Agent：

> 都犯完全一样的错。

那么：

$$
N=5
$$

也没有真正增加独立信息。

所以多 Agent 真正价值来自：

$$
Low\ Error\ Correlation
$$

### 错误相关性低。

这和投资组合分散：

> 完全一样。

---

# 四十七、你可以把 Agent 看成 Forecasters（预测者）

多个预测：

$$
p_1,p_2,\dots,p_n
$$

如果独立：

> 聚合能降噪。

如果高度相关：

> 增益很小。

所以：

$$
Number\ of\ Agents
\neq
Independent\ Opinions
$$

---

# 四十八、Aggregation（聚合）怎么做？

最简单：

$$
p=
\frac1N\sum_i p_i
$$

也就是：

> 平均概率。

但作者还讲：

### Weighted Aggregation（加权聚合）

### Log-Odds Aggregation（对数赔率聚合）

### Neyman Extremization（Neyman概率极化）

以及后续 calibration（校准）。

---

# 四十九、什么叫 Extremization？

假设三个 Agent：

$$
0.65,\ 0.68,\ 0.70
$$

简单平均：

$$
0.677
$$

但如果它们其实拥有部分独立证据：

> 平均会过度保守。

Extremization：

> 把概率从50%往外推一点。

例如：

$$
0.68\rightarrow0.75
$$

但要：

> 用历史 resolved forecasts（已解决事件）校准参数。

不能拍脑袋。

---

# 五十、Adversarial Debate 是什么？

### Adversarial Debate（对抗辩论）

作者 `07_adversarial_debate` 设计：

### Bull Agent（看多方）

### Bear Agent（看空方）

强制：

> 攻击彼此的证据。

目的不是：

> 生成一篇辩论文章。

而是：

> 看概率在反驳后是否变化。

---

# 五十一、什么时候 Debate 有价值？

如果初始：

$$
Bull=0.8
$$

Bear：

$$
0.3
$$

经过证据交换：

$$
Bull=0.65
$$

Bear：

$$
0.55
$$

说明：

> 双方学到了东西。

---

# 五十二、什么时候 Debate 是噪声？

如果只是：

> 重复观点。

或者：

> 两个 Agent 本质同一模型、同一证据。

那么对抗：

> 只是增加 Token 成本。

所以 Debate：

> 也必须做 ablation（消融）。

---

# 五十三、Supervisor Agent 是什么？

### Supervisor Agent（监督智能体）

它不是重新做全部研究。

而是：

> 检查各 Agent 的结果。

比如：

* 证据是否冲突；
* 来源质量；
* 是否有未解决问题；
* 概率是否合理。

然后输出：

> final forecast（最终预测）。

# 九十九、Agent其实只是最后的 Orchestration Layer

### Orchestration Layer（编排层）

它不替代：

* 因子；
* 模型；
* 回测；
* 风控。

它负责：

> 把这些模块自动串起来。

这对你非常重要。

因为你之前一直在想：

> **“如何设计一个自动挖掘因子的 Agent？”**

第24章其实给出的答案不是：

> 让 LLM 自己发明因子。

而是：

$$
\boxed{
让Agent成为
ResearchProcessController（研究流程控制器）
}
$$

这比单纯“AI生成策略”高一个层级。

# 最后一句话，把第24章真正讲透

第24章不是：

> **“教你搭几个 Agent 聊天。”**

它真正讲的是：

$$
\boxed{
如何把LLM从一个回答问题的模型，
变成一个可控制、可回放、可评估、
能调用工具完成复杂金融研究流程的执行编排器。
}
$$

完整思想是：

$$
\boxed{
Goal
\rightarrow
State
\rightarrow
Reason
\rightarrow
Tool
\rightarrow
Evidence
\rightarrow
Checkpoint
\rightarrow
Evaluate
\rightarrow
NextAction
}
$$

而真正专业的 Agent 系统还必须有：

$$
\boxed{
Memory
+
Registry
+
Calibration
+
Ablation
+
Observability
+
Security
+
HumanApproval
}
$$

最重要的一条原则是：

> **Agent 不应该替代确定性研究工具，而应该编排确定性研究工具。**

对你的量化研发来说，这几乎就是第24章最值得带走的答案：**真正优秀的 Factor Agent 不是“会生成更多因子”，而是能够记住过去研究、避免重复实验、自动调用正确验证流程、识别瓶颈、决定下一轮实验，并且留下完整可复现证据链。**
